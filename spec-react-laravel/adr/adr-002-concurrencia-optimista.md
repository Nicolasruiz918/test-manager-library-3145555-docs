# ADR-002 · Optimistic concurrency for book copies

**Implementation status (2026-10-14):** the historical audit proposals below remain separate from evaluator requirements. Adopted decisions are recorded in [the plan](../plan.md#implementation-record--t-12-and-t-13); actual results are linked in [the task register](../tasks.md#executed-implementation-evidence). The implementation uses schema-comment migration history, ephemeral book xmin, member coordination, atomic returns, logical deletion and frozen report aggregation. No new physical entity or business field was added.

- **Status:** accepted in the baseline; technology translated to Laravel/PostgreSQL. The audit proposals below have not been declared implemented or approved by the evaluator.
- **Source:** [baseline ADR-002](../../spec-.net/adr/adr-002-concurrencia-optimista.md), [HU-06/HU-07 and RNF-2](../../spec-.net/spec.md).
- **Context:** two operators can attempt to lend the last available copy simultaneously. Both must not confirm a loan for that single copy.
- **Decision preserved:** use optimistic concurrency. A book has a version token; saving against a changed version fails and a lending conflict returns **409 `BOOK_NOT_AVAILABLE`**, or the server retries once if a copy remains available. The existing `ck_book_available_range` constrains `0 <= available_copies <= total_copies`.
- **Alternatives rejected in the baseline:** pessimistic book-row locking and an in-memory counter. The original claim that locking a row serializes the entire library is factually too broad: row locks affect conflicting operations on the locked rows. That correction does not replace the accepted optimistic approach with a different one. [PostgreSQL 16 row locks](https://www.postgresql.org/docs/16/explicit-locking.html#LOCKING-ROWS).
- **Consequences:** the adapter must detect stale book state; a blind ORM save cannot demonstrate the version requirement. Repeated returns must preserve CA-07.2 and never increment inventory twice. The range constraint protects the numerical bounds, not the full correspondence between inventory and pending loan items.
- **Verification preserved:** two simultaneous requests for one last copy produce exactly one 201; RNF-2 requires the other request to receive 409. The final loan items and inventory must agree. Evidence requires independent concurrent operations against the real database, not a claim based on sequential requests.

### Technical basis and limits of the proposals

PostgreSQL exposes `xmin` for each row version. It is a transaction identifier, not a durable, monotonically increasing business version; identifiers can wrap. A proposal using it must keep tokens internal to short-lived persistence operations, not store them as history or publish them to React. [PostgreSQL 16 system columns](https://www.postgresql.org/docs/16/ddl-system-columns.html).

One schema-preserving coordination candidate is a transaction using `READ COMMITTED`, an exclusive lock on the existing member row for lending/returning, and book-version comparisons. Pending counts must be read **after** obtaining the member lock. If several books are changed, a stable id order reduces conflicting lock sequences. PostgreSQL documents the statement snapshots and update-condition rechecks relevant to this candidate. [PostgreSQL 16 transaction isolation](https://www.postgresql.org/docs/16/transaction-iso.html#XACT-READ-COMMITTED).

This is a candidate implementation approach, not new business scope or executed code. Its evidence should cover the original last-copy case, one eligible member with two pending non-overdue items requesting two different available books, simultaneous returns of the same item, distinct items of one book, a failed multi-item loan, and lending/returning against total edits or logical deletion. The same-item return must retain its existing business error; unspecified contention behavior requires clarification rather than an invented contract extension.
